Technical & Engineering Report

URSC — A Modular Engine for Long-Term LEO Trajectory Prediction and Orbit Determination

Architecture, force models, numerical methods, validation, and development roadmap
System: Java 17, Maven, zero runtime dependencies (JUnit 5 for tests only)
Reference architecture: Orekit (independent clean-room implementation)
Capabilities: Cowell numerical & DSST semi-analytical propagation; batch least-squares OD; full IAU-2006/2000B frames; CLI toolchain
Validation: Sentinel-3A/3B POEORB precise orbits (16 Oct 2024)
Test suite: 37 unit tests, all passing
Abstract. URSC is a from-scratch, dependency-free Java library for propagating and determining LEO satellite trajectories over long arcs. Every force model, integrator, atmosphere, frame model and output type is a pluggable component behind a small set of interfaces, assembled through a fluent configuration builder. The engine implements a complete perturbation stack (EGM96 geopotential to d/o 70, luni-solar third body, NRLMSISE-00 drag, conical SRP, solid/ocean tides, relativity), two propagators (adaptive Cowell and a numerically-averaged DSST mean-element method), a rigorous GCRF↔ITRF transformation, event detection, and a batch least-squares estimator. This report describes the software architecture, the implementation of each physical and numerical component, the validation against independent Sentinel-3 precise orbits (radial/cross-track held to metres over 24 h; batch fit reducing residuals ~8×), the error budget, and a prioritised roadmap of remaining work.

1  Objectives and design principles

URSC was built to determine and predict long-term LEO trajectories with a fully modular, inspectable, dependency-free codebase, using Orekit as an architectural reference but sharing no code.

Four principles drive the design:

  • Modularity. Every perturbation is a ForceModel; every atmosphere an Atmosphere; every integrator an ODEIntegrator; every frame realisation a selectable model. Components are composed, not hard-wired, so a force or a model can be added or swapped without touching callers.
  • Configurability. Every physical variable (degree/order, coefficients, areas, masses, tolerances, space weather) is an explicit input, set in code via a fluent builder or in a .properties scenario file.
  • Zero runtime dependencies. The entire stack — linear algebra, special functions, ephemerides, the NRLMSISE-00 thermosphere, frame transformations — is implemented in-house. Bundled reference data (gravity coefficients, nutation series, tide tables) ship as compressed classpath resources.
  • Auditability. Each model cites its governing reference (Montenbruck & Gill, IERS-2010 Conventions, SOFA) and is checked against published values in the test suite.

2.2  Core abstractions

The whole engine turns on a few small interfaces:

  • ForceModel — Vector3D acceleration(SpacecraftState). Every perturbation implements this one method; the propagator simply sums them.
  • Atmosphere — double getDensity(date, rBodyFixed), so the drag force is agnostic to the density model (exponential / Harris–Priester / NRLMSISE-00).
  • ODEIntegrator — a single adaptive or fixed step; the propagator drives it.
  • SampledPropagator — the common surface (step handlers, events, output type) that both the numerical and DSST propagators implement, so analysis tools accept either engine interchangeably.

Configuration is assembled with a fluent builder, PropagationConfig, which gathers the initial state, integrator, force toggles and output type and emits a ready propagator. The same configuration object is reused by the CLI, the comparison tool, the decay predictor and the estimator.

Normalisation & frames. EGM96 coefficients are stored fully normalised and de-normalised on load via the standard factor; the gravity acceleration is evaluated in ITRF (where the field is static) and rotated to GCRF each call. Drag likewise maps the inertial position to ITRF to read the density at the correct geodetic point. These per-call frame transforms are what make a correct GCRF↔ITRF model (§4) essential to overall accuracy.

3.1  Drag — the accuracy-limiting force

Drag uses the cannonball model with the relative velocity taken against a co-rotating atmosphere (vrel = v − ω⊕×r). Density comes from the pluggable atmosphere; with NRLMSISE-00 the drivers (daily F10.7, 81-day average F10.7a, daily Ap) are supplied by a SpaceWeatherProvider that is either constant or read from a CelesTrak CSSI file. The ballistic grouping CDA/m is the natural estimation parameter (§7, §9).

4  Reference frames and time scales

Propagation is performed in GCRF (pseudo-inertial). The GCRF↔ITRF transform has two selectable realisations: a fast sidereal-only SIMPLE model (GMST rotation, IAU-82 polynomial) and the default full IAU_2006 model implemented in Iau2006:

  • Precession — IAU-2006 Fukushima–Williams angles;
  • Nutation — IAU-2000B 77-term luni-solar series (~1 mas), coefficients in Nutation2000BData, ported from the SOFA reference;
  • Earth rotation — GAST (GMST + equation of the equinoxes) with UT1 from the EOP provider;
  • Polar motion — small-angle wobble matrix W(xp, yp).

EOP (UT1−UTC, polar motion) are injected through an EopProvider — either ConstantEop or a file-backed reader. Time scales (TimeScalesFactory) cover TAI, TT = TAI + 32.184 s, UTC with the full 1972–2017 leap-second table, GPS, and UT1. AbsoluteDate stores continuous TAI seconds from J2000, so epoch differences are exact across leap seconds — a subtle correctness point for long arcs. The IAU-2006 chain reproduces SOFA to ~10−13 rad in the test suite.

5  Numerical methods: integration and events

5.1  Dormand–Prince 5(4)

The recommended integrator is the adaptive Dormand–Prince 5(4) embedded Runge–Kutta pair (DOPRI5): a seven-stage, first-same-as-last (FSAL) scheme. The fifth-order solution is propagated and the difference against the embedded fourth-order solution drives per-step error control:

with step scaling by a safety factor (0.9), bounded growth/shrink factors [0.2, 5], and absolute/relative tolerances (validation used 10−7/10−9). The step automatically shrinks near perigee and in denser atmosphere and grows where dynamics are smooth. A fixed-step classical RK4 is also provided. Dense (cubic-Hermite) interpolation yields output on an arbitrary user grid without re-integrating.

5.2  Event detection

Events are located by a g-function sign change with bracketing and bisection refinement, supporting apside, node, altitude (re-entry) and eclipse detectors. This is what lets the decay/lifetime tools stop cleanly at a re-entry altitude and lets SRP/eclipse analyses find shadow boundaries.

6  Propagators: Cowell and DSST

6.1  Numerical (Cowell)

NumericalPropagator integrates the full osculating Cartesian state (r, v) under the summed forces using the chosen integrator, with step handlers, dense output and event detection. It is the high-accuracy workhorse used for the validation and OD below.

6.2  Semi-analytical (DSST, mean elements)

For multi-year and lifetime studies, resolving every ~100-minute revolution with Cowell is expensive. The DSSTPropagator implements a numerically-averaged mean-element method: it propagates the six mean equinoctial elements (a, ex, ey, hx, hy, λ) by orbit-averaging the variational equations:

(2)

At each large step, the osculating state is built at N points (default 24) around the current mean orbit; the perturbing acceleration (sum of the same ForceModels minus the two-body term) is evaluated at each; the element rates ∂E/∂v·γ are formed by finite difference of the equinoctial elements with respect to velocity (step 10−3 m/s); and these are averaged with the (1−e cos E) weight, with the mean longitude additionally advancing at the mean motion n(a). The result is mean elements, stepped in hours-to-a-day — roughly 20× faster than Cowell for long runs, reusing every force model. Short-period recovery (mean→osculating) is a documented follow-up.

7  Orbit determination (batch least squares)

BatchLeastSquares estimates a parameter vector — the initial state [r, v] and optionally the drag coefficient CD — by fitting the propagated trajectory to position observations through Gauss–Newton iteration. The design matrix (the partials of computed position with respect to the parameters) is formed by finite differences, so the estimator works with any force model and either propagation engine — no analytical variational equations are required. where ρi is the residual at observation i, sj the per-parameter scale (position 1, velocity 10−3, CD 10−2) that conditions the problem, and μ a tiny damping term. The step is accepted with step-halving backtracking (up to 6 contractions) and the iteration converges when the relative RMS improvement falls below 10−4. The linear system is solved by Gaussian elimination with partial pivoting. Observations are PositionObservations (GCRF, metres), here sampled from the POEORB precise orbit.

Interface. The estimator is driven through a PropagatorFactory lambda that rebuilds a seeded propagator from a parameter vector, so the same code fits either the Cowell or DSST engine, with any subset of forces.

8  Input/output and configuration

  • POEORB reader (PoeOrbReader) — parses CCSDS/Earth-Explorer AUX_POEORB *.EOF precise-orbit files: time-tagged ITRF state vectors plus the carried UT1−UTC offset. Drives both validate and fit.
  • Scenario files (ScenarioLoader) — .properties files where each force is an independent toggle with its own parameters; selects the propagator (numerical/dsst), integrator, orbit, spacecraft, output and re-entry event.
  • CSV writers — ephemeris export, including ground track.
  • TLE parser — approximate osculating seeding (no SGP4 mean-to-osculating recovery yet).
  • CLI (Cli) — zero-dependency sub-command dispatcher: propagate, decay, compare, tle, validate, fit, with ASCII plots and RTN error reporting in the terminal.

9  Validation methodology and results

9.1  Method

The validate command seeds the propagator from the first POEORB state (ITRF→GCRF with the file's own UT1), integrates forward under the full model with no fitting, and differences the propagated position against the precise orbit at each epoch, decomposing the error into radial, along-track and cross-track components. The fit command then runs the batch estimator against the same arc. Key engineering finding. The state-only fit is robust and well-conditioned (residual drops ~7–8×). The drag coefficient is not observable over a 6 h arc: it diverges to 5.26 (S3A) and −3.20 (S3B) — the normal matrix is ill-conditioned in the CD direction because, over ~4 revolutions, the drag partial is small and nearly collinear with the along-track state partials. The fix is longer arcs and/or an estimated empirical along-track acceleration with proper weighting (§12).

10  Verification: the automated test suite

mvn test runs 37 unit tests (all passing), checking physics and numerics against published values, not just internal consistency:

  • Loss-free orbit-element conversions and anomaly consistency; two-body energy conservation over 10 orbits.
  • Numerical vs analytical Keplerian agreement to sub-metre over an hour.
  • J2 nodal regression matching the secular formula dΩ/dt = −1.5 n J2 (Re/p)² cos i.
  • NRLMSISE-00 reproduces the official reference test case to 7 significant figures.
  • Frames reproduce SOFA to ~10−13 rad; time scales/leap seconds round-trip.
  • DSST matches two-body exactly, the J2 secular nodal rate to ~1%, and the Cowell secular SMA decay under drag to ~0.1 m over 3 days (mean-vs-mean).
  • Batch least squares recovers a perturbed initial state to ~mm and a known drag coefficient to within 0.05 from noise-free synthetic observations — confirming the estimator itself is correct (the Sentinel-3 CD divergence is an observability limit of the short real arc, not an estimator bug).
  • POEORB reader parses records, state-vector fields and the UT1−UTC offset.

12  Roadmap — what remains and how to improve

Prioritised by accuracy impact per unit effort. P1 highest.

P1  Accuracy of the dominant (drag) channel

  • Wire the file-backed historical space weather (CssiSpaceWeatherProvider, CelesTrak SW-All.csv) into validate/fit for the exact arc dates — the single biggest expected along-track improvement.
  • Estimate a ballistic scale factor (or piecewise-constant / empirical along-track acceleration via the existing EmpiricalAcceleration) over multi-day arcs, resolving the CD ill-conditioning of §9.2.
  • Add a box-wing (attitude-dependent area) model for drag and SRP.

P2  Estimation quality

  • Replace the finite-difference Jacobian with an analytical state-transition matrix (variational equations) — faster, more accurate, and a prerequisite for covariance.
  • Emit formal covariance and per-parameter sigmas; add observation weighting / data editing.
  • Add a sequential filter (EKF/UKF) alongside the batch estimator for real-time/streaming use and predictive uncertainty.
  • Fit directly to the raw onboard GNSS observations (Sentinel-3 GNSSRD product) rather than the reduced POEORB positions.

P3  Conservative-model fidelity & features

  • Default geopotential to 70×70; adopt a JPL DE ephemeris for Sun/Moon.
  • Add an IERS EOP file (finals2000A: polar motion + UT1 time series).
  • Solid-tide Step 2 (frequency-dependent) and pole tide; de Sitter relativity term.
  • DSST short-period recovery (mean→osculating) for metre-accurate semi-analytical output.
  • Proper SGP4 TLE seeding; additional atmospheres (JB2008, DTM2000).
  • Extend validation: full 26 h arcs for both satellites, DSST-vs-Cowell secular comparison, and a density-calibration study once real space weather is wired in.
